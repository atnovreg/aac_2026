# Jetson tmuxp 실행 정리

목표: 기존 `bash start.sh` 진입점을 Jetson용으로 전환하고, 실제 센서와 지도 위치추정의 실행·기록·종료를 한 세션에서 관리한다. 사용자가 현재 폴더 수정을 위임했으므로 기존 작업 폴더에서 변경한다. 기존 미커밋 소스는 덮어쓰지 않는다.

확인한 구성: Jetson `irdlsm@100.122.61.5`, Humble, `~/f1tenth_ws/live_indoor`, MID-360/위치추정 domain 43, 수동 PS5/VESC domain 42. `manual.car.yaml`은 수동 전용이며 속도/조향 환산은 임시 값이다. MPCC 출력은 정규화 전류이고 현재 VESC 전류/브레이크 입력은 비활성화되어 있다.

tmuxp만 기존 실험 스크립트에 감싸는 방법은 실행·종료를 여러 세션에 나누므로 채택하지 않는다. 실차와 시뮬레이션 YAML을 나누고, 하나의 실차 pane 실행 스크립트를 사용하는 방법을 선택한다. 전류 출력과 선택기 구현은 장치 계약이 다른 별도 제어 변경이므로 임의 구현하지 않는다.

## 구현 계획

- [x] 먼저 실행 테스트를 추가하고 실패를 확인한다. 누락된 실제 제어 명령, 잘못된 초기 자세, domain 분리, 실제 인수, 비정상 종료 보존을 확인한다.
- [x] 기존 YAML을 `simulation.yaml`에 보존한다. `config.yaml`은 실차 차량/센서/위치추정/MPCC/기록/모니터 창으로 바꾼다.
- [x] `jetson.env` 한 곳에 경로·초기 자세·실제 자율주행 출력 실행 파일을 모은다. `jetson.sh`에서 환경과 파일을 확인하고 각 pane을 `exec`한다.
- [x] `start.sh`는 기본 자율주행, `prepare`, `sim`, `check`를 지원한다. 자율주행 출력이 없으면 tmux 세션·기록 폴더 생성 전에 실패한다. prepare는 기존 수동/계산 환경임을 표시한다.
- [x] `auto.sh`는 같은 진입점으로 위임한다. `stop.sh`는 지정 세션에만 SIGINT를 전달하고, 아직 실행 중인 pane이 있으면 강제 종료하지 않는다. 기존 Gazebo harness는 simulation.yaml을 사용한다.
- [x] 사용법을 문서화하고 관련 회귀 검사와 격리된 tmux 동작을 검증한다. Jetson에서는 읽기만 수행하며 기존 실행을 중단하거나 차량을 구동하지 않는다.

검증 시 유의점: 실행 경로의 공백, 잘못된/빈 초기 자세, 오래된 tmux 서버 환경, 기존 차량 드라이버 중복, rosbag 종료 대기. 검사 통과는 위치추정 준비나 실차 주행 검증을 뜻하지 않는다.

## 진행 기록

- 기존 관리 검사: 프로젝트 acados Python 진입점에서 22개 통과. 시스템 Python 직접 실행은 casadi/PYTHONPATH가 없어 실패하므로 프로젝트 진입점을 사용한다.
- Jetson의 실제 실행 파일·보정 파일·실행 프로세스를 SSH로 읽었다. 원격 변경이나 새 차량 프로세스 실행은 하지 않았다.
- 신규 테스트의 실패를 먼저 확인한 뒤 구현했다. 기존 tmux 서버가 최신 환경변수를 받지 못하는 경우를 실제 격리 tmuxp에서 재현하고 실행별 `settings.env` 스냅샷으로 수정했다.
- 전체 관리 검사 34개 통과. 실제 tmux + 가짜 ROS 통합 검사에서 7개 pane의 설정 전달, 두 rosbag 메타데이터 마감, 다른 세션 보존을 확인했다. Bash 구문 검사, 두 YAML의 파싱·exec 확인, `git diff --check` 통과.
- 독립 코드 리뷰에서 추가 수정 사항 없음. 시스템 sandbox에서 tmux 서버 생성이 제한되어 통합 검사는 승인된 /tmp 격리 서버로 수행했다.
- 최종 원격 파일 대조를 위한 재접속은 timeout으로 실패했다. Jetson에 새 설정을 배포하거나 실제 prepare/자율주행을 실행한 것은 아니다. 실제 전류/제동 출력과 차량 선택기 구현·보정은 남아 있다.
